ATClient 设计思路详解

一个运行在 STM32F103C8（20 KB SRAM）上的通用 AT 客户端：全程异步、零动态内存、不依赖 HAL，也不认识任何具体模组的命令。本文逐条说明它为什么这样设计、换一种做法会出什么问题，以及每条设计落在哪个函数上。

00总览：AT 通信难在哪里

AT 看起来只是"发一行、收一行"。放到一颗 20 KB SRAM、没有 RTOS 的 MCU 上，真正的难点有四个。

  • 响应是异步的，而且分阶段。发出 AT+MIPSTART 后，OK 几毫秒就回来，CONNECT OK 可能要几秒。"收到 OK"并不代表"连上了"。
  • URC 随时插入。+MSUB:、CLOSED 可能夹在任何一条命令的响应中间，也可能在完全空闲时到达。
  • 同一个串口里混着文本和二进制。MQTT payload 里可能有 \r\n、0x00、>，按行切分就会切坏。
  • 资源和实时性都很紧。同一个主循环还要跑 SHT30 采样、蜂鸣器节拍、烟雾传感器和调试串口，任何一处"等一下"都会拖慢所有任务。

ATClient 的全部设计，都在回答同一个问题：在不阻塞、不 malloc 的前提下，怎样把这四件事做对。归纳起来是六条原则：

  1. 只依赖注入的 start_tx() 与 get_time_ms()，与 HAL、芯片解耦。§01
  2. 任何函数都不等待。Process() 只消费"已经发生"的事件。§02
  3. ISR 只搬字节、置标志，解析和回调全部在主循环中执行。§03
  4. 内存在编译期确定，每一种"装不下"都有返回码和计数。§04
  5. 通用层只懂"事务的形状"，命令语义由设备层通过描述符声明。§05–08
  6. 大 payload 流式透传，不整帧缓存。§12

设计要点

01传输层注入：ATClient 只认识两个函数指针

ATClient 不包含任何 HAL 头文件，也不保存 UART_HandleTypeDef。它对外部世界的全部要求，就是 ATClient_Transport 里的两个回调和一个上下文指针。

start_tx(context, data, length) 只负责启动一次异步发送并立即返回成功或失败；get_time_ms(context) 提供单调递增的毫秒时基。反方向的事件——收到字节、发送完成、传输错误——由适配层主动调用 ATClient_PushRx()、ATClient_OnTxComplete()、ATClient_OnTransportError() 通知进来。依赖方向因此是单向的：port → ATClient，ATClient 从不反向包含适配层的任何东西。

这样设计的好处

  • 可移植：换 MCU、换串口，甚至换成 USB CDC 或 RTOS 队列，只需重写适配层里的两个函数，ATClient.c 一行不动。
  • 可复用：同一份 ATClient 已承载 Air780E（MQTT），ML307C（HTTP）的设计也直接复用它，不再另建 AT 队列或行解析器。
  • 可测试：主机测试用 fake_start_tx 把"发送"记进数组，用一个变量充当时钟，24 个用例在 PC 上用 gcc 就能跑。
  • 可多实例：void *context 让同一套代码同时服务两个模组、两个串口，不依赖全局变量。

如果不这样设计

  • 库里直接调用 HAL_UART_Transmit_DMA(&huart2, …)：库与 STM32 HAL、与 USART2 死绑定，换一个串口就得改库；主机上无法编译，测试只能上板。
  • 库里直接调用 HAL_GetTick()：测试无法把时钟"快进"到 49.7 天的回绕点，这类 bug 只能等现场复现。
  • 没有 context 指针：只能用全局变量找到"当前串口"，无法再实例化第二个客户端。

02协作式非阻塞：Process() 只处理"已经发生"的事

库里没有 HAL_Delay，没有 while 等标志位，也没有阻塞式 UART 调用。每次 ATClient_Process() 只做有限的工作，然后把 CPU 还给主循环。

做法是把"等待"拆成"记下现在处于哪一步，下次再来看"：

  • 发送：StartNext() 调用 start_tx() 后立即把状态记为 TX_ACTIVE 并返回，发送完成由中断里的 OnTxComplete() 推进。
  • 等响应：状态停在 WAIT_RESPONSE，每次 Process 只解析环形缓冲里已经到达的字节，读到 head 就停。
  • 超时：只比较 now − started_ms，从不睡眠。测试 test_timeout_does_not_poll_or_block 断言每次 Process 只读一次时钟，证明内部没有轮询时钟的循环。

ATClient_Process() 内部的顺序同样经过考虑，每一步的位置都有原因：

lib/ATClient/src/ATClient.cL250–296一圈的完整流程
void ATClient_Process(ATClient *client)
{
    uint32_t now_ms;

    if (client == NULL)
    {
        return;
    }

    if (!client->has_active_request)
    {
        ATClient_StartNext(client);
    }

    if (client->transport_error_pending)
    {
        client->transport_error_pending = false;
        ++client->stats.transport_error_count;
        if (client->has_active_request)
        {
            ATClient_Complete(client, ATCLIENT_RESULT_TRANSPORT_ERROR);
        }
    }

    ATClient_ProcessRx(client);

    if (client->has_active_request &&
        client->state == ATCLIENT_STATE_WAIT_PROMPT && client->prompt_seen)
    {
        ATClient_StartPayload(client);
    }

    if (client->has_active_request)
    {
        now_ms = client->transport.get_time_ms(client->transport.context);
        if ((uint32_t)(now_ms - client->started_ms) >=
            client->active_request.timeout_ms)
        {
            ATClient_Complete(client, ATCLIENT_RESULT_TIMEOUT);
        }
    }

    if (!client->has_active_request)
    {
        ATClient_StartNext(client);
    }
}
  1. 先 StartNext()：空闲时尽早把队首事务发出去，后续解析到的回显和提示符才能归属到正确的事务。
  2. 再处理挂起的传输错误：放在 RX 解析之前，保证 TRANSPORT_ERROR 落在"出错的那一条"事务上，而不是被下一条命令背锅。
  3. ProcessRx() 消费全部已到达字节：这是有界循环，只读到 rx_head 为止，不等待新字节。
  4. 满足条件才发 payload：RX 解析可能刚刚看到 '>'，所以放在它之后判断。
  5. 最后判超时：先消费已到达的数据再判超时，"最后一毫秒到达的 OK"不会被误报为 TIMEOUT。
  6. 收尾再 StartNext()：本圈有事务结束时，下一条命令在同一圈内立即发出，不白等一圈。

这样设计的好处

  • 主循环延迟有上界：Process 的耗时只与"本圈新到了多少字节"有关，与模组多久才回复无关。等待 AT+MIPSTART 最长 30 s 的期间，SHT30 采样、蜂鸣器节拍、烟雾传感器照常运行。
  • 不需要 RTOS：没有线程栈、互斥锁和优先级反转，20 KB SRAM 省下的空间更可观。
  • "等待"变成显式状态：可以查询（ATClient_IsIdle()），也可以测试——测试里直接断言某次 Process 之后 completion_calls == 0。

如果不这样设计

  • 阻塞发送 + while 等 OK：一条命令就把主循环卡住几百毫秒到 30 秒，期间蜂鸣器、传感器全部停摆。设计文档专门指出：工程早期 main.c 里的 HAL_Delay(1700) 会让 AT 状态机约 2 秒才运行一次，因此集成时被移除。
  • 用延时实现超时：模组掉电时每条命令都要等满超时，看门狗很可能在这段时间里复位整机。
  • 在中断回调里"顺手推进下一步"：逻辑散落在 ISR 和主循环两处，难以推理，还违背了"ISR 不执行用户代码"的约束。

03ISR 与主循环分工：单生产者 / 单消费者环形缓冲

中断里只做一件事：把字节拷进 rx_buffer。所有解析都在主循环里完成，两者之间用一个无锁的 SPSC 环形缓冲连接。

rx_head 和 rx_tail 是两个只增不减的 uint32_t 计数器：ISR 只写 head，主循环只写 tail，任何一方都不会对"对方的变量"做读-改-写。待处理字节数等于 head − tail，无符号减法天然处理计数器回绕；数组下标等于 计数 % 1024。缓冲满时，PushRx() 丢弃新来的字节、累加统计并返回 RX_OVERFLOW，已缓存但未解析的旧数据保持不动。

ATClient_Result ATClient_PushRx(ATClient *client,
                                const uint8_t *data,
                                size_t length)
{
    size_t copied = 0U;
    uint32_t head;
    uint32_t tail;

    if (client == NULL || (data == NULL && length != 0U))
    {
        return ATCLIENT_RESULT_INVALID_ARGUMENT;
    }

    head = client->rx_head;
    tail = client->rx_tail;
    while (copied < length &&
           (uint32_t)(head - tail) < ATCLIENT_RX_CAPACITY)
    {
        client->rx_buffer[head % ATCLIENT_RX_CAPACITY] = data[copied];
        ++head;
        ++copied;
    }
    client->rx_head = head;

    if (copied != length)
    {
        ++client->stats.rx_overflow_count;
        client->stats.rx_dropped_bytes += (uint32_t)(length - copied);
        return ATCLIENT_RESULT_RX_OVERFLOW;
    }

    return ATCLIENT_RESULT_OK;
}

void Air780E_UartPort_RxEvent(UART_HandleTypeDef *huart, uint16_t position)
{
    uint16_t previous;

    if (huart != &huart2 || port_state.client == NULL ||
        position > AIR780E_UART_RX_DMA_CAPACITY)
    {
        return;
    }

    previous = port_state.rx_cursor;
    if (position == AIR780E_UART_RX_DMA_CAPACITY)
    {
        Air780E_UartPort_PushSpan(previous, AIR780E_UART_RX_DMA_CAPACITY);
        port_state.rx_cursor = 0U;
    }
    else if (position >= previous)
    {
        Air780E_UartPort_PushSpan(previous, position);
        port_state.rx_cursor = position;
    }
    else
    {
        Air780E_UartPort_PushSpan(previous, AIR780E_UART_RX_DMA_CAPACITY);
        Air780E_UartPort_PushSpan(0U, position);
        port_state.rx_cursor = position;
    }
}

这样设计的好处

  • 无需临界区：没有共享的 count，就不存在 ISR 与主循环同时读-改-写的竞争，也不用关中断。
  • ISR 时间可预期：一次 PushRx() 只是有界拷贝（不超过一个 DMA 块），不会因为某行特别长或某个回调特别慢而拖长中断。
  • 回调永远不在中断里执行：回调里可以放心打日志、提交新事务、访问非 volatile 状态。
  • 溢出时丢新保旧：已缓存的半行不会被悄悄改写，rx_overflow_count 和 rx_dropped_bytes 能直接说明丢了多少字节。

如果不这样设计

  • 共享 count：ISR 里 count++、主循环里 count--，被中断打断就会丢一次更新（图 3 下半部分），表现为偶发的"多了或少了一个字节"，极难复现。
  • 在中断里解析 AT：中断耗时随数据长度变化，还会在中断上下文调用上层回调，回调里任何一次 printf 都可能让下一段 DMA 数据溢出。
  • 满了就覆盖旧数据：解析器看到的是拼接错位的行，比一个明确的溢出错误难查得多。

  • 失败先于成功：更保守——宁可把可疑的行判为失败，也不误报成功。
  • 事务判定先于 URC：CLOSED 既注册为 URC，也是 MIPSTART 的 failure token。在建链期间出现时，由正在等待的事务立即拿到失败结果，而不必等 30 s 超时。
  • URC 先于 on_line：+MSUB: 这类异步通知即使夹在某条命令的响应中间，也不会被误当成那条命令的输出。

09唯一的完成出口：先清状态，再回调，只回调一次

所有结束路径——OK、ERROR、CME / CMS、failure token、超时、传输错误、行过长、命令构造失败——都汇入同一个 ATClient_Complete()。

它的顺序是固定的：先把 on_complete 和 callback_context 取到局部变量，再 memset 清空 active_request、复位状态和 token 下标，最后才调用回调。开头的 has_active_request 检查是一道守卫，重复调用会直接返回。

static void ATClient_Complete(ATClient *client, ATClient_Result result)
{
    ATClient_CompleteCallback callback;
    void *context;

    if (!client->has_active_request)
    {
        return;
    }

    callback = client->active_request.on_complete;
    context = client->active_request.callback_context;
    memset(&client->active_request, 0, sizeof(client->active_request));
    client->has_active_request = false;
    client->state = ATCLIENT_STATE_IDLE;
    client->command_length = 0U;
    client->prompt_seen = false;
    client->skip_prompt_space = false;
    client->success_token_index = 0U;

    if (callback != NULL)
    {
        callback(context, result);
    }
}

这样设计的好处

  • 恰好回调一次：同一圈 Process 中，ProcessRx() 已因 OK 完成事务，随后的超时判断看到 has_active_request == false 就不会再报一次 TIMEOUT。test_timeout_does_not_poll_or_block 在超时后再调一次 Process，断言回调次数仍是 1。
  • 回调里看到的是一致的状态：此时 ATClient_IsIdle() 的结果是准确的；回调里再次进入 ATClient（例如提交新事务）也不会看到"已结束但仍标记为活动"的半截事务。
  • 新事务零延迟：回调里 Submit 的事务会在同一次 Process 末尾的 StartNext() 中立即发出。
  • 不残留旧指针：已完成事务的 payload、context 指针被清零，不会被后续逻辑误用。
  • 新增错误路径成本低：清理逻辑只写一遍，任何新路径只需调用 ATClient_Complete(client, 某结果)。

如果不这样设计

  • 各条路径各自清理：迟早有一条路径漏掉 prompt_seen 或 success_token_index 的复位，下一条命令就继承了上一条的半截状态。
  • 先回调再清状态：回调期间事务仍标记为活动，IsIdle() 给出错误答案；若回调间接再次进入 ATClient，同一事务可能被再次完成、再次回调。
  • 没有守卫：响应和超时在同一圈到达时回调两次，设备层状态机会连跳两步。

11URC 前缀注册表

URC（非请求结果码）是模组主动上报的行，可能在空闲时到达，也可能夹在任何一条命令的响应中间。ATClient 用最多 8 个"前缀 → 回调"的注册项来分发它们。

注册时预先用 strlen 算好 prefix_length，分发时每个注册项只做一次长度比较和一次 memcmp，第一个命中即返回。同一前缀重复注册会原地更新回调和上下文（幂等），不会多占槽位。空闲时收到的行同样经过 URC 分发。

  • 4100 B payload 不占额外 RAM：只需 384 B 行缓冲装帧头，数据直接从已有的 1024 B 环形缓冲交给回调。

这样设计的好处

  • 描述符只有 72 B，复制它的代价很小，调用者可以把 request 放在栈上或反复复用。
  • payload、topic、前缀这些可能很大的数据不复制，RAM 占用与消息大小无关。

如果不这样设计

  • 什么都复制：队列要为每条事务预留 payload 空间，RAM 成倍增长。
  • 什么都不复制：调用者栈上的 request 在函数返回后失效，队列里留下悬空指针。
  • 契约不写明：调用者在发布完成前就复用 payload 缓冲，模组收到的是下一条消息的内容，而且只在高负载时才出现。

14走读：一次 QoS 1 的 MQTT 发布

把前面的设计放在一条真实事务里：Air780E_MqttPublish() 发布一条 QoS 1 消息，从提交到回调，依次经过 4 个活动状态、两次 DMA 发送和两次 TX 完成中断。

  1. 提交（§05、§06）：Air780E 填好描述符（prompt_byte = '>'、payload 指针、OK → PUBACK、超时 30 s）后调用 ATClient_Submit()，描述符被复制进队列，函数立即返回。
  2. 发命令（§02、§05）：下一次 ATClient_Process() 中，StartNext() 出队、调用 build_command 写入 command_buffer、追加 \r\n、记下 started_ms，调用 start_tx() 后返回。
  3. 等提示符（§03、§07）：DMA 发完后，中断调用 OnTxComplete() 把状态推到 WAIT_PROMPT；"> " 到达时中断只调用 PushRx()。
  4. 发 payload（§07、§13）：下一圈 Process 在 ProcessRx() 中按字节识别出 '>'，随后 StartPayload() 把调用者的缓冲区原样交给 DMA。
  5. 分阶段确认（§08）：OK 命中 success_tokens[0]，事务继续；PUBACK 命中最后一个 token，进入 Complete(OK)。
  6. 完成（§09）：Complete() 清空活动事务后回调 on_complete(OK)，Air780E 把发布标记为完成；同一圈末尾 StartNext() 取出下一条排队事务。

如果中途出现 PUBACK FAIL 或 CLOSED，第 5 步会命中 failure token，以 ERROR_RESPONSE 结束；如果 30 s 内等不到任何一步，则以 TIMEOUT 结束。无论哪种情况，都只走 ATClient_Complete() 这一个出口。

16边界与改进建议

以下是阅读源码时发现的隐含前提和可以加固的地方。它们在当前 Air780E 的使用方式下大多不会触发，但在移植或扩展时值得留意。

#现象 / 前提可能的后果建议
1state 由中断和主循环共同写入：OnTxComplete() 在中断里改 state，而 StartNext() / StartPayload() 在 start_tx() 返回之后才写入 TX_ACTIVE / PAYLOAD_TX_ACTIVE。若 TX 完成中断恰好落在这两步之间（至少要隔一个字节时间 ≈ 87 µs，需主循环被更高优先级中断拖住），它看到的是旧状态而被忽略。事务停在 TX_ACTIVE，直到超时仿照 transport_error_pending：ISR 只置一个 volatile 的"发送完成"标志，由 Process 推进；或在调用 start_tx() 之前先写好状态、失败时回退。跨上下文的 state、transport_error_pending 也宜声明为 volatile。
2RX 容量必须是 2 的幂：下标 = 计数 % 容量，计数在 232 处回绕。1024 满足条件，但没有编译期检查。若改成 1000 之类的值，累计收满约 4 GB 字节时出现一次数据错位，几乎不可能复现增加 _Static_assert((ATCLIENT_RX_CAPACITY & (ATCLIENT_RX_CAPACITY - 1U)) == 0U, "…")，并可把 % 换成 & (容量 − 1)。
3成功 token 严格按顺序匹配：若 CONNECT OK 先于 OK 到达，它会被当成中间行。事务等不到期望的 token，最终超时Air780E 手册中的顺序是固定的，当前可以接受；需要兼容乱序时，可改为"集合匹配 + 已命中位图"。
4事务判定优先于 URC：CLOSED 同时是 URC 和 failure token 时，建链期间的 CLOSED 只会结束事务，Air780E_ClosedUrc() 不会被调用。"连接关闭"的处理分散在两处Air780E 已在 Air780E_FinishMqttOperation() 中为失败的连接操作安排重连；新的设备层需要同样在失败回调里处理。
5超长行一律结束当前事务，即使那一行其实是无关的 URC。偶发的误失败（LINE_TOO_LONG）丢弃前检查已缓存的前缀是否属于已注册 URC，只有非 URC 行才结束事务。
6skip_prompt_space 在 StartPayload() 中才置位。若 '>' 和其后的空格在同一次 ProcessRx() 中被消费，空格会先进入行缓冲，最后作为一行 " " 交给 on_line。多出一行噪声；若模组在最终响应前不输出 \r\n，"OK" 会变成 " OK" 而无法匹配在识别到提示符字节时就置位 skip_prompt_space。
7BUSY、CANCELLED 结果码已预留，但还没有取消接口。用户主动断开时，已排队的命令仍会执行需要时增加 ATClient_CancelQueued()，对被丢弃的事务回调 CANCELLED。
8长度帧探针每追加一个字节都从头扫描帧头。帧头最长 383 B，最坏约 7 万次字节比较；注册项越多，开销线性增加。72 MHz 下可忽略，注册项增多后值得关注探针对本行返回 NO_MATCH 后，本行不再询问该注册项。
